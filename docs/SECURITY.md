# Безопасность QuietChat

## Что защищает приложение

QuietChat шифрует текст, растр и короткое аудио на устройстве перед ручной передачей. Для открытия нужны секретный ключ получателя и заранее проверенный открытый ключ отправителя. Статический хостинг получает запросы файлов приложения; прикладные данные не отправляются через сеть приложением. Само наличие интернет-соединения и деятельность браузера, ОС/расширений не контролируются сайтом.

Контейнер `QC1` — версия собственного **формата**, построенного на штатных криптографических примитивах libsodium; это не новый шифр. См. [полную спецификацию](FORMAT.md). Секретный ключ содержимого независим для каждого сообщения. `crypto_box_easy` защищает конверт этого ключа; `crypto_secretstream_xchacha20poly1305` защищает содержимое. Обязательны проверка каждого блока, его порядка, последнего тега и отсутствия лишних данных. До полной проверки данные не поступают в просмотрщик/проигрыватель.

Нет цифровой подписи, доказательства авторства для третьих лиц, прямой секретности или постквантовой защиты. Получатель способен создать сообщение, криптографически совместимое с этой парой участников. Компрометация долговременного секретного ключа одной стороны и знание открытого ключа другой позволяет расшифровать ранее перехваченные контейнеры. Смена ключа защищает будущий обмен только после независимой проверки нового отпечатка; старые сообщения от этого не становятся безопаснее.

## Что не защищает приложение

- Мессенджер, через который передаётся контейнер, видит факт общения, участников, время отправки и приблизительный размер. Заголовки, сетевые адреса и учётные записи этого мессенджера QuietChat не скрывает.
- Получатель может сохранить, записать или переслать расшифрованное. Запрет скриншотов и надёжное «самоуничтожение» недостижимы для такого сайта.
- Заражённая ОС, вредоносное расширение, модифицированный браузер, клавиатура, захват экрана, украденные ключи, буфер обмена и его облачная синхронизация остаются угрозами.
- Повторная доставка старого корректного контейнера сама по себе не криптографическая ошибка. Нет сохранённой истории, счётчика сеансов или защиты от повторов.
- Удаление файловых тегов не убирает лица, документы, адреса на фотографии, биометрические особенности голоса и фоновые звуки.
- Потерянные ключи или забытый пароль восстановить некому. Серверного «сброса пароля» нет.

## Доверие к сборке и хостингу

Весь исполняемый код и libsodium входят в `dist/`. Пакеты имеют точные версии и lock-файл; сборка выполняется локально или в GitHub Actions. Это уменьшает число внешних источников кода во время работы, но не устраняет риск цепочки поставки.

Компрометация репозитория, хостинга, npm-зависимости, сборочного инструмента или GitHub Actions может подменить приложение и перехватить секреты при следующем открытии. Подменённое приложение может показывать ожидаемую версию и хеш. Кэш и хеш, полученные от того же сайта, не дают независимой гарантии подлинности. Для более строгого сценария проверяйте исходники/артефакт по независимому доверенному каналу, собирайте в доверенной среде и работайте без сети. Независимый аудит проекта не проводился.

Service worker при установке получает только статические файлы из встроенного списка, проверяет SHA-256 и сообщает готовность после полной проверки. Он не получает ключи/медиа и не реализует runtime-кэш пользовательских данных. В кэш допускаются только GET-ответы собственных фиксированных URL. При утрате отдельного файла восстановление из сети разрешается только с хешем той же сборки; новая несовпадающая версия не смешивается с открытым сеансом.

Обновления остаются ожидающими до закрытия всех вкладок приложения: `skipWaiting()` отсутствует. `clients.claim()` вызывается только по сообщению первого посещения с совпадающей версией и проверенным полным кэшем уже активного worker, до разрешения создания/разблокировки ключей. Ожидающий worker при этом не активируется. На сообщение `ACTIVATE_UPDATE` worker отвечает требованием закрыть вкладки, не активирует себя. Версия UI должна совпадать с версией ответа `VERIFY_CACHE`, прежде чем показывать офлайн-готовность. SHA-256 здесь проверяет целостность относительно полученного manifest, а не личность издателя.

GitHub Pages имеет общий origin для проектов пользователя: например, `/QuietChat/` и другой `/project/`. Пути ограничивают область service worker, но **не создают отдельную границу безопасности origin** для localStorage и скриптов. Не размещайте недоверенные приложения на том же origin; отдельный выделенный домен уменьшает этот риск. Зашифрованная локальная копия остаётся доступной для копирования и офлайн-перебора атакующему с доступом к origin. Разблокированные секреты нельзя считать защищёнными от активного кода того же origin.

## CSP и браузерная поверхность

Политика находится в `<meta http-equiv="Content-Security-Policy">` до скриптов. По умолчанию источники запрещены. Скрипты/стили/Worker/manifest разрешены только с собственного origin; `blob:` разрешён для локальных изображений и аудио. Для WebAssembly libsodium требуется `wasm-unsafe-eval`; `unsafe-eval` и `unsafe-inline` не включены. В исходном коде интерфейса не используются `eval`, вставка пользовательского HTML и автоматическое выполнение Markdown. Текст вставляется через текстовые DOM API, внешние ссылки не открываются автоматически, загружаемые SVG/HTML не считаются допустимыми изображениями.

`connect-src 'self'` нужен для статической подготовки PWA и локальной сборки библиотеки; это не разрешение отправлять сообщения на сервер. Код обработки содержимого не делает сетевых запросов. CSP — дополнительный барьер, а не защита от подмены разрешённого собственного скрипта. У элементов формы выключены автозамена/проверка орфографии по доступным браузерным атрибутам; принудительно управлять сторонней клавиатурой невозможно.

GitHub Pages не предоставляет проекту произвольную настройку всех HTTP-заголовков. CSP в meta не поддерживает защиту `frame-ancestors` и не эквивалентна CSP-заголовку; `X-Frame-Options`, COOP/COEP и серверный `Permissions-Policy` здесь не обещаются. Поэтому защита от clickjacking на чистом Pages ограничена. Referrer-Policy задаётся meta. На хостинге с настройкой заголовков можно дополнительно задать `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` и запрет неиспользуемых возможностей. Локальный сервер предпросмотра добавляет nosniff/no-referrer и ограничивает camera/geolocation.

## Секреты, память и резервная копия

В обычном сеансе ключи, контакты, текст, исходные файлы, подготовленные копии и расшифрованные результаты находятся в памяти. Нет истории сообщений, черновиков, IndexedDB для содержимого, автоматического копирования или сохранения. Секреты не добавляются в URL, уведомления, журналы, консоль или телеметрию.

Постоянная локальная запись возникает только после явного сохранения зашифрованной копии `QCB1`. Внутри — ключевая пара и контакты, снаружи — ограниченные параметры KDF, соль, nonce и шифротекст. Пароль не сохраняется. Argon2id v1.3 использует фиксированный профиль: 64 МиБ памяти, opslimit 3; импорт сначала проверяет максимальный размер, версию и точное соответствие профилю. Никакого автоматического ослабления параметров. XChaCha20-Poly1305 аутентифицирует заголовок копии; повреждение параметров/шифротекста отклоняется.

Дорогая криптография выполняется в отдельном Worker. Блокировка/отмена завершают Worker, останавливают аудио и микрофон, отзывают object URL, очищают доступные Uint8Array и ссылки интерфейса. Но неизменяемые JS-строки, внутренние копии движка, WebAssembly/native-буферы, DOM, сборщик мусора, память процесса, swap и резервные снимки ОС недоступны для гарантированного стирания. Завершение Worker не является доказательством физической очистки памяти. Таймеры и фоновые события могут задерживаться; снимок переключателя приложений может произойти раньше маскировки. Ручная блокировка перед уходом уменьшает окно риска.

## Медиа и ресурсы

При импорте проверяется размер файла, фактическая сигнатура/структура и допустимый тип. Для растра число пикселей проверяется до декодирования; приватная копия создаётся из пикселей и не переносит исходные теги. Для аудио проверяется поддерживаемая структура, ограничения длительности/каналов и результат декодирования; приватная копия строится из PCM. Поддержка native-декодирования зависит от браузера. Ошибка очистки не вызывает молчаливый переход на оригинал.

Протокол ограничивает размеры до больших выделений памяти; размер дополнения и число частей также ограничены. Шифрование/расшифрование не раскрывает проверенные только частично сообщения. Лимиты не делают браузерные кодеки неуязвимыми: специально повреждённый файл может использовать неизвестную уязвимость native-декодера. Обновлённый браузер и ОС остаются необходимыми.

## Проверка и сообщения об ошибках

Автотесты используют синтетические данные и временные ключи. Никогда не отправляйте в issue действующие секретные ключи, парольные фразы, расшифрованное содержимое или скриншоты с ними. Для воспроизведения проблемы создайте отдельный тестовый профиль, опишите версию сборки/браузера и шаги. Не включайте реальные данные в логи тестов. Результаты автоматического прогона не заменяют независимый аудит и ручную проверку целевых устройств.
